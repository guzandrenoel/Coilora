# Coilora API Design

## 1. API principles

- Base path: `/v1`.
- HTTPS only.
- JSON for normal requests and responses.
- UUID or UUIDv7 identifiers generated by a trusted client/server policy.
- UTC ISO-8601 timestamps.
- Cursor pagination for changing collections.
- `Idempotency-Key` for retryable creates, uploads, generation and review submissions.
- Optimistic concurrency through `revision` or `If-Match`.
- Consistent problem-details error responses.
- OpenAPI is the contract source and generates TypeScript clients first, followed by Swift and Kotlin clients when native applications begin.
- The authenticated subject comes from the verified token, never a request-supplied `ownerId`.

### Current implementation boundary

The implemented API includes health and current-user access, course and notebook operations within the current product rules, notebook-page listing and creation, document creation and listing, upload sessions and completion, and PDF read sessions. Other endpoints in this document describe the target API and are not necessarily available yet.

## 2. Authentication flow

Authentication is provided by Supabase Auth.

### Web

1. Offer email/password verification first; self-hosted SMTP is configured separately.
2. Prefer a server-side/secure-cookie session integration.
3. Apply CSRF protection to cookie-authenticated mutations.

### Future native applications

1. iPad may use native Sign in with Apple and exchange the Apple identity token and nonce for a Supabase session.
2. Android uses the same email account authority initially; platform sign-in is a later documented exception.
3. Store native refresh/session secrets in Keychain or the Android Keystore-backed secure storage.
4. Send the access token in `Authorization: Bearer <token>` to the Coilora API.

### API verification

NestJS verifies signature, issuer, audience, subject, expiration and account status. It then creates a request principal such as:

```json
{
  "userId": "uuid",
  "role": "student",
  "accountStatus": "active",
  "subscriptionTier": "student"
}
```

Do not create a second independent Coilora JWT system.

## 3. Authorization model

### MVP roles

- `student`: manages only personally owned resources.
- `admin`: manages accounts and system configuration; content access is denied by default.

### Resource rules

- Every course, notebook, document, chat, study item and review record belongs to a user.
- A student can access a child resource only if its complete ownership chain resolves to that student.
- Knowledge retrieval must apply ownership filters before vector or full-text ranking.
- Signed storage URLs are generated only after an ownership check.
- Administrative support sees operational metadata by default, not document content.
- Any future emergency content access needs an explicit reason, short-lived authorization and immutable audit event.

Future sharing introduces `notebook_members` with `viewer` and `editor`; it must not overload the `role` field used for system administration.

## 4. Endpoint catalog

### Profile and account

```text
GET    /v1/me
PATCH  /v1/me
GET    /v1/me/usage
POST   /v1/me/export
GET    /v1/me/exports/:exportId
POST   /v1/me/deletion-request
DELETE /v1/me/deletion-request
```

### Courses and notebooks

```text
POST   /v1/courses
GET    /v1/courses
PATCH  /v1/courses/:courseId
DELETE /v1/courses/:courseId

POST   /v1/notebooks
GET    /v1/notebooks?courseId={courseId}
PATCH  /v1/notebooks/:notebookId
DELETE /v1/notebooks/:notebookId
GET    /v1/notebooks/:notebookId/pages?page={page}
POST   /v1/notebooks/:notebookId/pages
GET    /v1/notebooks/:notebookId/documents
```

Notebook-page creation accepts a page name and `paperStyle` as `blank`, `dotted`, `ruled`, `grid`, or `cornell`. Optional document placement inserts the note after a PDF page. Page lists are ordered by position and return at most 50 items plus a `nextPage` value. Page updates support renaming and bookmark changes.

### Documents and pages

```text
POST   /v1/notebooks/:notebookId/documents
GET    /v1/notebooks/:notebookId/documents
PATCH  /v1/notebooks/:notebookId/documents/:documentId/bookmark
POST   /v1/documents/:documentId/upload-session
POST   /v1/documents/:documentId/upload-complete
POST   /v1/documents/:documentId/read-session
POST   /v1/documents/:documentId/preview-session
PATCH  /v1/documents/:documentId/page-count
GET    /v1/documents/:documentId
GET    /v1/documents/:documentId/status
GET    /v1/documents/:documentId/pages
GET    /v1/documents/:documentId/pages/:pageNumber
POST   /v1/documents/:documentId/reprocess
DELETE /v1/documents/:documentId
POST   /v1/documents/:documentId/export
```

Creating a document reserves metadata; the upload session returns a signed destination. Upload completion verifies the actual storage object. The read-session endpoint checks ownership and returns short-lived access for the in-app PDF reader. The reader records a validated PDF page count after loading. Background processing and the remaining document endpoints are planned.

Document lists include `bookmarked` and `revision`. The bookmark PATCH accepts only `{ "bookmarked": true | false }` and checks the owner, active notebook, and non-deleted uploaded-or-later document. Whole-document bookmarks are independent of PDF page bookmarks.

The preview-session endpoint uses the same owner, active-notebook, uploaded-status, revision, and canonical private-storage-path checks as read-session. It also accepts the supported image, TXT, and Markdown formats. It returns a five-minute signed source URL with `private, no-store`; previews are rendered locally and do not create public thumbnail objects. The read-session endpoint remains PDF-only.

### Annotations and synchronization

```text
POST   /v1/sync/push
GET    /v1/sync/pull?cursor={cursor}&limit={limit}
GET    /v1/notebooks/:notebookId/pages/:pageId/annotations
POST   /v1/notebooks/:notebookId/pages/:pageId/annotations
DELETE /v1/notebooks/:notebookId/pages/:pageId/annotations/:annotationId
GET    /v1/documents/:documentId/annotations/bookmarks
GET    /v1/documents/:documentId/pages/:pageNumber/annotations
POST   /v1/documents/:documentId/pages/:pageNumber/annotations
DELETE /v1/documents/:documentId/pages/:pageNumber/annotations/:annotationId
PUT    /v1/documents/:documentId/pages/:pageNumber/bookmark
DELETE /v1/documents/:documentId/pages/:pageNumber/bookmark
```

The web editor sends one durable normalized stroke after pointer completion and renders an optimistic copy while the request is pending. Both annotation POST endpoints accept an optional UUID `id`. The client reuses that ID when retrying a failed save. A duplicate primary key is treated as an existing save only after an owner-scoped lookup verifies the same notebook page, or the same document and PDF page. It cannot return an annotation from another target or owner. Clients that omit `id` retain server-assigned IDs.

The continuous notebook viewer keeps active, pending, and failed strokes mounted outside the visible page window. Failed strokes remain visible with a retry action; they are not persisted in an offline browser outbox. The app back buttons block while ink is pending, and browser unload warns before discarding it. The future native editor may batch Pencil or stylus changes into durable operations and add snapshot compaction for recovery.

PDF bookmark listing uses owner-scoped keyset batches of 500 to return bookmarks beyond the database's default row limit, up to the supported 5,000-page document boundary.

The shared viewer uses the existing notebook-page, document-list, read-session, annotation, and bookmark endpoints. It combines metadata into one reading order rather than flattening or rewriting the PDF file. Only nearby pages and thumbnails render, and a lease-based pool retains at most two PDF sources. No new database migration or unified-content endpoint is required for this presentation layer.

## 5. Example contracts

### Create document

```json
POST /v1/notebooks/{notebookId}/documents
{
  "title": "Hematology Lecture 03",
  "originalFilename": "lecture-03.pdf",
  "mediaType": "application/pdf",
  "byteSize": 15423310,
  "sha256": "hex-digest",
  "sourceType": "pdf"
}
```

```json
201 Created
{
  "id": "uuid",
  "status": "awaiting_upload",
  "revision": 1
}
```

### Citation

```json
{
  "id": "uuid",
  "sourceSpanId": "uuid",
  "documentId": "uuid",
  "documentTitle": "Hematology Lecture 03",
  "pageNumber": 12,
  "quotePreview": "Iron is transported in plasma...",
  "boundingBoxes": [
    { "x": 0.132, "y": 0.445, "width": 0.622, "height": 0.041 }
  ],
  "timestampStartMs": null
}
```

Quote previews are short navigation aids, not substitutes for storing provenance.

### Review answer

```json
{
  "operationId": "uuid",
  "reviewedAt": "2026-08-27T14:15:00Z",
  "grade": "again",
  "responseDurationMs": 7300,
  "shownRevision": 4
}
```

The server returns the new FSRS scheduling state and next due date. Replaying the same operation ID must not produce a second review.

## 6. API-facing resource model

The canonical storage strategy and entity relationship diagram live in [Database and storage](./05_DATABASE_AND_STORAGE.md). The fields below define the stable resource concepts exposed through the API.

### Identity and organization

#### `profiles`

- `user_id` PK/FK to auth user
- `display_name`
- `role`
- `account_status`
- `timezone`
- `locale`
- `subscription_tier`
- `created_at`, `updated_at`, `deletion_requested_at`

#### `devices`

- `id`, `owner_id`
- `platform`, `app_version`
- `push_token_ciphertext` or platform notification token reference
- `last_seen_at`, `revoked_at`

#### `courses`

- `id`, `owner_id`
- `name`, `color`, `term`, `archived_at`

#### `notebooks`

- `id`, `owner_id`, `course_id`
- `title`, `description`, `exam_date`
- `created_at`, `updated_at`, `archived_at`, `revision`

#### `notebook_pages`

- `id`, `owner_id`, `notebook_id`
- `position`
- `paper_style`: `blank`, `dotted`, `ruled`, `grid`, or `cornell`
- `created_at`, `updated_at`

### Documents

#### `documents`

- `id`, `owner_id`, `notebook_id`
- `title`, `original_filename`, `source_type`, `media_type`
- `status`, `page_count`, `byte_size`, `sha256`
- `source_object_path`, `sanitized_object_path`
- `parser_version`, `indexed_at`, `failure_code`
- `created_at`, `updated_at`, `deleted_at`, `revision`

#### `document_pages`

- `id`, `owner_id`, `document_id`, `page_number`
- `width_points`, `height_points`, `rotation`
- `preview_object_path`, `text_status`, `ocr_confidence`

#### `source_spans`

- `id`, `owner_id`, `document_id`, `page_id`
- `sequence`, `text`, `normalized_text`
- `bounding_boxes` JSONB
- `timestamp_start_ms`, `timestamp_end_ms`
- `search_vector`, `embedding`
- `parser_version`, `embedding_version`

Index `owner_id`, parent foreign keys, `search_vector`, and the vector column appropriately.

### Annotations

#### `annotations`

- `id`, `owner_id`, `document_id`, `page_id`
- `type`: `ink`, `highlight`, `text`, `shape`, `image`, `occlusion_mask`
- `geometry` JSONB in normalized/PDF coordinates
- `style` JSONB
- `content` JSONB
- `z_index`
- `created_by`: `student`, `ai_accepted`, `imported`
- `revision`, `created_at`, `updated_at`, `deleted_at`

#### `annotation_operations`

- `operation_id` PK
- `owner_id`, `device_id`, `annotation_id`
- `base_revision`, `action`, `payload`
- `occurred_at`, `accepted_at`, `result_revision`

Operation rows can be archived/compacted after snapshots and retention requirements are satisfied.

### AI and learning

#### `highlight_suggestions`

- `id`, `owner_id`, `document_id`, `page_id`, `source_span_id`
- `status`, `category`, `reason`, `confidence`
- `geometry`, `model_snapshot`, `prompt_version`
- `created_at`, `decided_at`, `revision`

#### `chats` and `messages`

- Chat: `id`, `owner_id`, `notebook_id`, `title`, timestamps.
- Message: `id`, `chat_id`, `role`, `content`, `status`, model/prompt versions, token/cost metadata, timestamps.

#### `message_citations`

- `message_id`, `source_span_id`
- `claim_index`, `rank`, `retrieval_score`

#### `study_items`

- `id`, `owner_id`, `notebook_id`, `type`, `status`
- `front`, `back`, `explanation`, `choices` JSONB
- `image_object_path`, `occlusion_masks` JSONB
- `tags`, `difficulty`
- `generated_by`, `model_snapshot`, `prompt_version`
- `created_at`, `updated_at`, `revision`

#### `study_item_sources`

- `study_item_id`, `source_span_id`, `relationship`

#### `review_states`

- `study_item_id` PK, `owner_id`
- FSRS `difficulty`, `stability`, `retrievability` or required library state
- `due_at`, `last_reviewed_at`, `lapse_count`, `review_count`
- `scheduler_version`, `revision`

#### `review_events`

- `id`/`operation_id`, `owner_id`, `study_item_id`
- `grade`, `reviewed_at`, `response_duration_ms`
- scheduling state before and after
- `device_id`, `created_at`

Review events are append-only except for privacy deletion.

### Operations

#### `jobs`

- `id`, `owner_id`, `type`, `status`
- `resource_type`, `resource_id`
- `progress`, `attempt_count`, `failure_code`
- `created_at`, `started_at`, `completed_at`

#### `entitlements`

- `owner_id`, `product_id`, `source`
- `status`, `valid_from`, `valid_until`, `original_transaction_reference`

#### `audit_events`

- `id`, `actor_id`, `actor_type`, `action`
- `target_type`, `target_id`
- `reason`, `request_id`, `ip_hash`
- `created_at`

Audit logs must not contain document text or assistant prompts.

## 7. Error format

```json
{
  "type": "https://docs.coilora.app/errors/document-not-ready",
  "title": "Document is not ready",
  "status": 409,
  "code": "DOCUMENT_NOT_READY",
  "detail": "The document is still being indexed.",
  "requestId": "uuid",
  "retryable": true
}
```

Stable machine codes are more important than exposing internal exceptions.

## 8. Rate and quota controls

Apply different buckets for:

- Authentication attempts.
- Signed upload-session creation.
- Stored bytes and file count.
- OCR pages per billing period.
- Transcription minutes.
- Assistant requests and tokens.
- Generation requests and generated items.
- Export creation.

The API should return remaining usage or a durable usage endpoint rather than surprise users only after a limit is reached.

## 9. API testing requirements

- Contract tests from OpenAPI.
- Ownership/IDOR tests for every identifier-bearing route.
- RLS tests with two unrelated users.
- Idempotency replay tests.
- Optimistic concurrency tests.
- Pagination consistency tests.
- Signed URL expiry and ownership tests.
- Webhook signature and replay tests.
- Cross-device review and annotation synchronization tests.
- Account deletion and export completeness tests.
